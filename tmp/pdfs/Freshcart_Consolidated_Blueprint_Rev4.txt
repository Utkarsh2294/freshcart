Executive Summary
Freshcart is a quick-commerce grocery platform — Zepto/Blinkit-style storefront, doorstep delivery, your own catalog only — built around one
flagship feature: an AI agent that turns a typed (or voice-searched) dish request into a priced, editable, swappable cart pulled entirely from your
own product database. This revision locks in three things that were still open in earlier drafts:
• The visual design is finished, not aspirational. Every screen in this plan is built against the exact tokens and component anatomy of
freshcart_redesign_prototype.html — the same sidebar, topbar, category chips, gradient hero, deals grid, and persistent cart panel
you already have working as a static mock, in both light and dark mode. Phase 0 below is a porting job, not a design exercise.
• The AI pipeline has one honest, scoped exception. Every model in this project is still a self-hosted, fine-tuned open-weight model you
control — except recipe generation, which calls Kimi K3 via API. That's a deliberate trade against reality: Kimi K3 isn't self-hostable by an
individual (2.8T parameters, no full open weights at time of writing), and a homegrown 4B fine-tune consistently underperforms it on recipe
quality. One exception, clearly labelled, doesn't compromise the "no AI wrapper" story for the other seven self-hosted components.
• Pramarsha is a second, independent AI system riding on top. A temporal-behavior recommendation engine — already built, already
mining real event data — gets its own dedicated, visually distinct Home surface (teal/green gradient, reserved for it alone) rather than being
folded into the generic recommendation rail.
What still makes this a strong resume/hackathon project, not a generic clone: the AI layer is a real multi-model pipeline (NLU, retrieval-free
generation via a frontier model API used surgically, a fine-tuned semantic matcher, a hybrid recommender, and a genuinely novel deterministic
pack-selection algorithm) sitting on a production-shaped relational core with wallet, referral, live tracking, and PWA installability already solved.
SECTION 2
Scope Clarifications & Honest Assumptions
"Self-trained AI" still means fine-tuning, not training from scratch — for the six components that remain self-hosted (text intent/servings
NER, ingredient-matching embeddings, review sentiment, recommendation ranking, and optionally cooking-mode TTS), the plan is unchanged
from Rev 2.0: download open-weight checkpoints, fine-tune on your own curated data, serve from your own FastAPI microservices, zero API
keys involved.
On the Kimi K3 exception, specifically. Kimi K3's full weights were not openly released as of this writing, and even once released, a 2.8T-
parameter model is far beyond single-GPU self-hosting for a student project. Using it via API for recipe generation only is a deliberate, scoped
exception to the zero-third-party-API principle — not a reversal of it. Every other AI component in this system, including the ingredient matcher that
grounds Kimi's output against your real catalog, stays self-hosted. Say this plainly in any interview or demo: "one exception, chosen deliberately, for
the one component where a frontier model earns its keep."
Compute reality is lighter than Rev 2.0 assumed. Dropping the self-hosted Whisper fine-tune and the QLoRA-tuned recipe LLM removes the
two heaviest GPU workloads from the original plan. What's left to fine-tune — a small NER model, a sentence-transformer, and a DistilBERT
sentiment classifier — comfortably fits a free-tier Colab/Kaggle GPU for training and a CPU or single consumer GPU for inference.
Maps/payments/SMS remain infrastructure, not AI — same reasoning as before: Razorpay/Stripe test mode for payments, MSG91-style
OTP for auth, and self-hosted OpenStreetMap + Leaflet for the live-tracking map. These don't conflict with the "no AI wrapper" principle because
they're not AI.
Plain JavaScript, still, everywhere except the Python AI layer. React + Vite + Tailwind on the frontend, Node/Express (ESM) on the
backend, no .ts /.tsx file anywhere. The compensations from Rev 2.0 — Joi validation at every API boundary, PropTypes on every
component, mandatory unit tests on anything touching money — are unchanged and, if anything, more load-bearing now that the design system
also has zero compile-time enforcement (a color token typo won't be caught by a compiler either — Phase 0 below is written to make that hard
to get wrong).
Everything below is scoped for a solo developer (or you + 1-2 teammates) across roughly 24-26 weeks, MVP-first — slightly shorter than Rev
2.0's 27 weeks, mostly thanks to the two removed ML services.

SECTION 4
System Architecture
Same separation-of-concerns principle as Rev 2.0: the Node API never talks to any model directly — it calls one internal AI Orchestrator, which
fans out to specialized FastAPI microservices and, for exactly one hop, to the external Kimi K3 API. That hop is isolated behind a single client
module so a Kimi outage degrades gracefully (retry once → "couldn't generate that recipe, try rephrasing" state) instead of taking down
checkout or browsing.
• Everything self-hosted, except one labelled exception. Model weights for the NER, matcher, sentiment, and recommendation
components sit in a local cache directory, fine-tuned by you. The only runtime call to any external AI API in the entire system is
kimiRecipeClient.js → Kimi K3 .
• Graceful degradation, unchanged principle. If any AI microservice — or Kimi K3 itself — is slow or down, the customer can still browse,
search, and check out normally.
• Two independent AI layers now coexist on Home. The Cook-with-AI pipeline (Kimi K3 → matcher → pack selection) and the Pramarsha
temporal-behavior engine (external, already built) both write to the Home screen but never call into each other — Pramarsha's mining
pipeline has its own event log and its own serving endpoint, untouched by this blueprint.
• No compiler, so contracts are written down explicitly. Every service boundary — Node↔FastAPI, Node↔Kimi K3, frontend↔Node — is
documented in /contracts as an explicit JSON schema. Treat that folder as load-bearing, not optional documentation.

Phase 5 — Ingredient Matching, Quantity-Aware Pack Selection &
Weeks 14-16
Auto-Cart MERGES OLD PHASE 5 + NEW LOGIC
Goal: Turn Kimi K3's ingredient list into real, in-stock, correctly-sized products sitting in the cart — fully editable, only from products actually in
stock at the user's resolved dark store. This phase now includes genuinely new deterministic pack-selection logic that didn't exist in Rev 2.0.
MASTER PROMPT — Phase 5
You are a full-stack engineer connecting Phase 4's Kimi K3 output to the live
product catalog. All code stays plain JavaScript.
STEP 1 — INGREDIENT MATCHING (self-hosted, `matcher-service` FastAPI, or extend
recommendation-service): for each ingredient name+unit, (a) exact/fuzzy match via RapidFuzz against
product names and a maintained ingredient-alias table, (b) if confidence < 0.75, fall back to
semantic search using `sentence-transformers/all-MiniLM-L6-v2` embeddings over product titles
(precomputed, refreshed on catalog change), (c) among matched candidates in the right category AND in
stock at the user's dark_store_id, call the recommendation-service's /best-in-category endpoint
(Phase 2) to shortlist candidates, (d) cache resolutions in ingredient_product_map keyed on
(ingredient_name, dark_store_id). Do NOT change this step based on Kimi K3 — it only replaces recipe
text, never the grounding.
STEP 2 — QUANTITY-AWARE PACK SELECTION (new, pure deterministic logic — never
hand this to an LLM): implement `selectPack(neededQty, candidatePacks) -> {productId, qty, matchType,
note}`:
a. If any single pack's size P >= needed qty Q exists, pick the smallest such P. Tag "exact_match"
if P <= Q*1.2, else "closest_match".
b. If no single pack covers Q but n = ceil(Q/P) packs of the same product cover it reasonably,
recommend qty=n, tag "closest_match", with a note like "3 x 200g packs ≈ 600g — closest match to
500g".
c. If the only available pack is far larger than Q (e.g. only a 5kg bag for a 50g need), still
surface qty=1, tagged "oversized" with a note like "smallest available pack — more than you need."
Never leave an ingredient unresolved without an explicit tag.
d. If NO product matches at all, mark unavailable and exclude from auto-cart.
Write unit tests covering all four branches.
STEP 3 — FINALIZE ENDPOINT (Node): POST /ai/cook-this/finalize {ingredients,
dark_store_id, user_id} → calls matcher-service, runs each result through selectPack(), inserts matched
products into cart_items with source='ai_recipe' inside one DB transaction, and writes an
ingredient_product_map row per resolution (match_type, qty, note).
STEP 4 — RESULT SCREEN (uses Phase 0's RecipeResultChecklist component exactly):
checkbox per row (checked by default), matched product name + pack size, the match-type badge
(exact/closest = green, oversized = amber, per Phase 0's semantic-color tokens), the human-readable
note, and price. Sticky footer shows running total of checked items + "Add checked items to cart."
Any ingredient below 0.75 confidence shows "not sure about this one — tap to search manually" instead
of auto-selecting.
EDGE CASES: ingredient matches nothing in the catalog ("not available — skip");
matches something globally but nothing in stock at this dark store ("out of stock nearby," distinct
from "not available at all"); the same ingredient needed by two concurrent recipe sessions (idempotent
insert); user edits quantity on the result screen (recompute price live with shared/money.js, never
re-call any AI service).
DELIVERABLE: matcher-service, selectPack() with unit tests for all 4 branches, the finalize endpoint,
the wired-up result screen, and a manual test log of 15 recipes against the seeded catalog documenting
match accuracy and how many resolved to an in-stock product.
Definition of Done: all 15 test recipes produce a fully populated, checked-by-default checklist with at most 2 "not available" items each ·
selectPack() unit tests pass for all 4 branches · editing quantity updates price instantly with zero AI calls · the result screen visibly shows at least
one exact-match and one closest-match badge in a real end-to-end test · out-of-stock-nearby is visually distinct from not-in-catalog.

cart. The only non-deterministic, non-self-hosted step in this entire chain is the single Kimi K3 call — everything before and after it is auditable,
cached, and under your control.

SECTION 14
Testing, Deployment & Scaling Notes
• Test pyramid: unit tests on selectPack() , the matcher's scoring math, and all money-math (highest-value tests given the no-TypeScript
decision); integration tests on each FastAPI service and on kimiRecipeClient.js 's retry/cache logic; end-to-end tests (Playwright/
Cypress) on the full cook-this → cart → checkout journey plus wallet-and-payment.
• Latency budget: under 3 seconds total for the AI pipeline is realistic once recipe_cache and the matcher cache are warm — the Kimi K3
network hop is now the dominant cost, not local model inference, which is the opposite latency profile from Rev 2.0.
• Cost-aware scaling: GPU needs are lighter than Rev 2.0 — no Whisper, no recipe-LLM serving. Budget instead for Kimi K3 API usage;
track cost per recipe generation and cache-hit rate from day one.
• Data flywheel: ai_interaction_logs still lets you improve the self-hosted models (NER, matcher, sentiment) post-launch from real
usage, even though recipe generation itself isn't something you fine-tune anymore.
• No compiler, so lint/test discipline is not optional — unchanged from Rev 2.0: a failing ESLint or Jest run in CI is a hard blocker on
every PR.

SECTION 16
Risks & Honest Limitations
• Kimi K3 is a real, non-optional external dependency now. Unlike every other AI component, this one is out of your control: rate limits,
pricing changes, or an outage directly affect the flagship feature. The circuit breaker and cache in Phase 9 bound this risk; they don't
eliminate it. Say this plainly if asked in an interview — it's a deliberate trade, not an oversight.
• Photo-based dish input is genuinely gone from this revision, not deferred by accident. If a judge or interviewer asks "can it work from a
photo," the honest answer is "not in this build — the reference design and the Kimi K3 pipeline are text-first, and adding vision back in is a
clean, independent module if there's time."
• Cold-start data problem — unchanged from Rev 2.0: ratings, reviews, and the Pramarsha cohort signal all need real usage to be
meaningful; seed with synthetic-but-realistic data for the demo and say so upfront.
• Pramarsha's quality is inherited, not built here. This blueprint doesn't audit or improve its mining logic — if its recommendations are
weak, that's a pre-existing constraint, not something Phase 7 can fix without violating the "don't touch its schema/logic" rule.
